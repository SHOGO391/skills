# ui-copy — 画面は自分を説明しない。商品の中身は削らない

土台は artouc/stop-describing-ui（MIT）。原文の 9 規則は references/stop-describing-ui.md にある。
元の規則を会員向けの予測サイトに当てたとき、2 つの事故が起きた。売り物の説明まで削って戻す羽目になったのと、
社内でしか通じない呼び名が画面に残ったのに規則が拾わなかったこと。実例は references/examples.md。
このスキルはその 2 つを防ぐ形に直してある。

## なぜ分類が先か

画面の文は、利用者が操作の前に読まされるもの。だから操作まわりの文は「読まないと失敗する」ものだけ残す。
ただし、どのサービスにも操作の文言とは別に **商品そのもの** の文がある。予測サイトなら戦略の説明と成績、
SaaS なら料金表の但し書きや機能の売り文句、EC なら商品説明。ここは「説明が多い」のではなく売り物で、
削る権限は作り手にしかない。逆に、内部の呼び名（モデル名・テーブル名・基盤のサービス名・処理の段）は
操作でも売り物でもなく、利用者には意味が無い。

なので、削る前に全部の文字列を 4 つに分ける。分類が先、規則は後。

## 手順

1. **対象の文字列を全部集める。** 画面に出る文字だけ。HTML の本文・`title`・`placeholder`・`aria-label`、JS/TSX の文字列リテラルと JSX の本文、ヘルプの表。コメントや console は対象外。
   `python scripts/ui_copy_lint.py <files...>` を先に回すと、候補が行番号つきで出る（下の「機械の点検」）。
2. **4 つに分類する。** 迷ったら「利用者がこの文を読まないと、何かを失敗するか」で決める。

   | 分類 | 例 | 扱い |
   |---|---|---|
   | A 操作の文言 | ボタン・列名・空の状態・読み込みエラー・ログインの案内・設定の説明・トースト | 規則 1〜9 で削る／言い換える |
   | B 商品の中身 | 商品やプランの説明、戦略の説明と成績、印や指標の意味、見方のコツ、版（バージョン）の表示と履歴、ブランドの決まり文句 | **触らない。** 短くしたいときは別に提案し、承認を取ってから |
   | C お金・法・取り返しのつかない注意 | 免責、課金・解約・削除・通知の結果、法令で要る表示、数字の読み方の但し書き | **残す。** 短くしてよいが消さない |
   | D 内部の漏れ | モデルや処理の呼び名、ファイル名・テーブル名、基盤のサービス名、作り方の説明、列名の括弧書き、長い `title` | 利用者の言葉に替えるか消す（規則 10〜12） |

3. **変更案を before/after の表で出し、承認を取る。** 列は「場所（ファイル:行）／分類／before／after／根拠の規則」。
   承認前にファイルを編集しない。戻し作業は編集より高くつく。
4. **承認が出たら編集し、変更履歴に書く。** repo に UI の変更履歴があればそこへ。何を残したか（B・C）も 1 行書く。
5. **最後にもう一度 lint を回す。** D の漏れが 0 になるまで。

## 規則 1〜9（A 操作の文言に当てる）

元の 9 規則。英語の before/after は references/stop-describing-ui.md。

1. **機能を説明しない。** 見出し・コントロール・ラベルが画面の目的を言っている。「〜ページです」「This page allows you to…」は消して、動作の名前にする。
2. **動詞は具体的に。** 「新規」「管理」「設定」「OK」「New」「Manage」は、実際に起きることと対象に替える。「ログイン」より「解錠する」、「保存」より「この端末だけに保存」、「New」より「Connect repository」。
3. **結果は一番大事な 1 つだけ。** ただし削除・課金・通知のような取り返しのつかない結果は必ず残す（分類 C）。
4. **裏側の動きを書かない。** どこに保存されるか、何が記録されるか、同期・キャッシュ・読み直しの間隔は利用者の関心ではない。
5. **同じコントロールで戻せるなら、戻し方を書かない。**
6. **ページがもう言っていることを書かない。** タイトル・ナビ・節の構造で分かることは消す。
7. **無いものを書かない。** 「まだ〜はありません」「No items yet」は画面が示す。例外は「試して失敗する制限」で、それはアイコンつきの短い 1 行にする。
8. **有効にする方法を文で書かず、ボタンかトグルを置く。** 「設定からプランを変更してください」→ ボタン［プランを変更］。
9. **文だけに頼らない。** 段落は 1 行ずつに割り、アイコンと余白で構造を見せる。`／` `＝` `：` `→` `|` `!` を区切り・矢印・強調に使わない。

## 規則 10〜12（D 内部の漏れ・この版で足した規則）

10. **内部の呼び名を出さない。** モデル名・処理の段・テーブル名・ファイル名・基盤のサービス名・社内の略号は、利用者の言葉に替える。
    「発走前の板×購入AIの2段目」→「発走前のオッズと AI の予測」、「race_data.json の読み込みに失敗」→「この日の読み込みに失敗」、「Supabase に保存」→ 書かない。
    例外: 利用者に見せると決めた **版の表示**（v3.1 のバッジ、更新履歴）は分類 B。
11. **列名・ラベルは短く、補足を付けない。** 列名の括弧書き「AI印（発走前の板×…）」、長い `title` のツールチップ、見出しの注記は全部外す。
    意味の説明はヘルプの表に 1 行で書く。表の列は見比べる場所で、読む場所ではない。
12. **新しい情報は、同じ種類の情報が並んでいる場所に置く。** 表に似た指標の列があるなら、新しい指標もその表の列。設定に似た項目があるなら、同じグループの 1 行。
    別ページ・別パネル・別カードは、依頼者が「別に」と言ったときだけ。置き場所を決める前に、既存の列定義・設定の一覧・ヘルプの表を読む。

## 言語ごとの癖

日本語（A で特に出やすいもの）

- 「〜してください」の案内文 → 多くはボタンに置き換えられる（規則 8）。残すときは「〜を入力」の体言止め。
- 「〜です」「〜します」で終わる説明文 → ほぼ規則 1 か 6 で消える。
- 「※」「補足:」「注:」で始まる行 → まず分類 C かどうかを見る。C なら残し、A なら 1 行に割る。
- 「／」「＝」「：」で繋いだ凡例 → 1 項目 1 行、アイコン先頭（規則 9）。
- 丁寧語の埋め草「ご利用ください」「ご確認ください」「〜となります」→ 消す。
- 「なし」「ありません」の空表示 → 規則 7。表示自体を消すか、行動のボタンだけ残す。

英語

- "This page allows you to…", "Here you can…" → 規則 1。見出しとコントロールに任せる。
- "Please…", "Go to Settings and…", "Click here to…" → 規則 8。コントロールを置く。
- "Your data is stored securely and synced…" → 規則 4。残すのは利用者が困る制限だけ。
- "simply", "easily", "just", "seamlessly" → 埋め草。消す。
- "No projects yet." + 説明文 → 規則 7。空の状態は行動のボタン 1 つ。

## 機械の点検

```
python scripts/ui_copy_lint.py web/index.html src/App.tsx
python scripts/ui_copy_lint.py --terms .ui-copy-terms.txt --keep .ui-copy-keep.txt --json out.json web/*.html
python scripts/ui_copy_lint.py --preset myapp web/index.html
python scripts/ui_copy_lint.py --lang en --only T10,T8 src/**/*.tsx
```

- 画面に出る文字列を集め、規則の番号つきで候補を出す。日本語と英語の両方。**判定はしない**。人と AI が分類する材料。
- `T10 内部の語` だけは当たれば終了コード 1。commit 前のフックや CI に置ける。既定の語は scripts/terms/general.txt（拡張子・基盤のサービス名・内部の仕組みの語）。
  プロジェクト固有の語は repo に `.ui-copy-terms.txt` を置いて `--terms` で足す。何度も使う一覧は scripts/terms/private/NAME.txt に置けば `--preset NAME` で読める。
  private/ は git の対象外。モデル名などの内部の語の一覧そのものを公開リポジトリに載せない。
- `--keep` に「残すと決めた文字列」のファイルを渡すと、その文字列は出さない（分類 B・C の控え）。

## 書くとき（新規の文言）

点検と同じ規則で書く。順序は、まずコントロールを置けないか考え、次に 1 行で済まないか考え、最後に文を書く。
文を書いたら、分類 A なら規則 1〜9 を自分で通す。利用者向けの説明（分類 B）を新しく書くときは、
その画面の既存の B の文体（体言止めか、です・ます か、数字の書式、英語なら sentence case か title case か）に合わせる。
